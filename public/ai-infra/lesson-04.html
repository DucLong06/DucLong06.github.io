Lesson 04 / 05

Đọc config.json tính tham số và bộ nhớRead config.json: parameters and memory

Từ config.json ra tham số, byte weight và số request vừa một máy.From config.json to parameters, weight bytes and requests per machine.

Quy ước số: mọi con số trong bài in đúng như output của course/m1/calc.py hoặc của lệnh lab.

Number convention: every number is printed exactly as course/m1/calc.py or the lab command outputs it.

1

Mục tiêuGoal

Học xong, chỉ từ config.json bạn tính được tổng tham số, tham số active, dung lượng weight ở BF16 / FP8 / NVFP4, byte KV mỗi token, và số request tối đa vừa một máy; sai lệch so với model.safetensors.index.json bằng 0 byte với model BF16.

After this lesson, from config.json alone you can compute total and active parameters, weight size at BF16 / FP8 / NVFP4, KV bytes per token, and the maximum number of requests that fit one machine, with zero bytes of error against model.safetensors.index.json for BF16 models.

2

Vì sao cầnWhy it matters

Đội vận hành có hai DGX Spark (128 GB bộ nhớ hợp nhất mỗi máy). Hai yêu cầu đến cùng tuần: (1) “serve Qwen3-30B-A3B cho trợ lý code, context 32K, được bao nhiêu người dùng cùng lúc?”; (2) “chạy DeepSeek-V3 trên hai máy này được không?”. Trả lời bằng tính tay trước khi tải hàng trăm GB: Qwen3-30B-A3B ở BF16 chứa được 14 request 32K, ở FP8 được 23. DeepSeek-V3 ở FP8 cần 671 GB weight, không vừa hai máy (256 GB); kể cả NVFP4 cũng cần 377 GB.

The team has two DGX Sparks (128 GB unified memory each). Two requests arrive in the same week: (1) “serve Qwen3-30B-A3B as a coding assistant at 32K context: how many concurrent users?”; (2) “can we run DeepSeek-V3 on these two machines?”. Answer by hand before downloading hundreds of GB: Qwen3-30B-A3B in BF16 fits 14 requests of 32K, in FP8 it fits 23. DeepSeek-V3 in FP8 needs 671 GB of weights and does not fit two machines (256 GB); even NVFP4 needs 377 GB.

Công thức (model dense kiểu Llama/Qwen3)

Formulas (dense Llama/Qwen3-style model)

  • Attention mỗi tầng: d·n_Q·d_h (q) + 2·d·n_KV·d_h (k, v) + n_Q·d_h·d (o), cộng q_norm/k_norm nếu có (Qwen3).
  • FFN mỗi tầng: 3·d·f. Norm: 2·d mỗi tầng + d cuối.
  • Tổng = L × (attention + FFN + norm) + V·d × (1 hoặc 2).
  • Weight byte = tổng × byte/tham số: BF16 2, FP8 1, NVFP4 0.5625 (4 bit + một scale FP8 cho mỗi 16 giá trị). NVFP4 ở đây là ước lượng: checkpoint thật giữ vài lớp ở BF16 nên lớn hơn một chút.
  • KV byte/token = 2·L·n_KV·d_h·byte (GQA/MHA); MLA xem bài 05.
  • Số request tối đa: B_max = ⌊(M_device − M_weight − M_workspace) / M_KV,request⌋.
  • Attention per layer = d·n_Q·d_h (q) + 2·d·n_KV·d_h (k, v) + n_Q·d_h·d (o), plus q_norm/k_norm when present (Qwen3).
  • FFN per layer = 3·d·f; norms 2·d per layer + d final.
  • Total = L × (attention + FFN + norms) + V·d × (1 or 2).
  • Weight bytes = total × bytes per parameter: BF16 2, FP8 1, NVFP4 0.5625 (4 bits plus one FP8 scale per 16 values). NVFP4 here is an estimate: real checkpoints keep a few layers in BF16 and come out slightly larger.
  • KV bytes per token = 2·L·n_KV·d_h·bytes (GQA/MHA); MLA is in lesson 05.
  • Max requests: B_max = ⌊(M_device − M_weight − M_workspace) / M_KV,request⌋.

Số request vừa một máy

Requests per machine

Ví dụ trong sách, RTX 4090 24 GB, workspace 2 GiB, Qwen3-8B BF16: 9 request ở 4K, 4 ở 8K, 2 ở 16K. Với một DGX Spark, giả định ngân sách 0.85 × 128 GB = 108.80 GB (phần còn lại cho hệ điều hành, vì bộ nhớ hợp nhất dùng chung với CPU) và workspace 2 GiB:

The book's example, an RTX 4090 24 GB with 2 GiB workspace and Qwen3-8B BF16, fits 9 requests at 4K, 4 at 8K and 2 at 16K. For one DGX Spark, assuming a budget of 0.85 × 128 GB = 108.80 GB (the rest for the OS, since unified memory is shared with the CPU) and 2 GiB workspace:

Key notesKey notes

  1. Mọi con số bộ nhớ bắt đầu từ config.json: d, L, V, n_Q, n_KV, d_h, f, và các trường MoE/MLA.
  2. Tổng tham số quyết định dung lượng weight; tham số active quyết định FLOPs mỗi token (≈ 2 × active).
  3. Byte weight = tham số × byte/tham số; FP8 bằng nửa BF16, NVFP4 khoảng 0.5625 byte nếu tính cả scale.
  4. Kiểm chéo bằng model.safetensors.index.json: total_size của checkpoint BF16 phải bằng 2 × tổng tham số.
  5. B_max = ⌊(bộ nhớ − weight − workspace) / KV mỗi request⌋; context dài gấp đôi thì B_max giảm gần một nửa.
  6. Trên DGX Spark, bộ nhớ hợp nhất chia với hệ điều hành: phải tự đặt ngân sách (ví dụ --gpu-memory-utilization) trước khi tính.
  7. Quantize weight giải phóng chỗ cho KV: Qwen3-30B-A3B 32K từ 14 lên 23 request khi BF16 sang FP8.
  1. Every memory number starts from config.json: d, L, V, n_Q, n_KV, d_h, f, plus the MoE/MLA fields.
  2. Total parameters set weight capacity; active parameters set FLOPs per token (≈ 2 × active).
  3. Weight bytes = parameters × bytes per parameter; FP8 is half of BF16, NVFP4 about 0.5625 bytes counting scales.
  4. Cross-check with model.safetensors.index.json: the total_size of a BF16 checkpoint must equal 2 × total parameters.
  5. B_max = ⌊(memory − weights − workspace) / KV per request⌋; doubling context roughly halves B_max.
  6. On a DGX Spark, unified memory is shared with the OS: set a budget yourself (for example --gpu-memory-utilization) before computing.
  7. Quantizing weights frees room for KV: Qwen3-30B-A3B at 32K goes from 14 to 23 requests when moving from BF16 to FP8.

Tự kiểm traSelf-check

1. Qwen3-30B-A3B có 30,532,122,624 tham số nhưng chỉ 3,353,032,704 active. Con số nào quyết định model có vừa máy không?Qwen3-30B-A3B has 30,532,122,624 parameters but only 3,353,032,704 active. Which number decides whether it fits the machine?

Lời giảiAnswer

Tổng tham số. Mọi expert phải nằm trong bộ nhớ vì token nào cũng có thể chọn bất kỳ expert nào; active chỉ quyết định FLOPs mỗi token (6.71 GFLOP).

The total. Every expert must be resident because any token may pick any expert; active only sets FLOPs per token (6.71 GFLOP).

2. DeepSeek-R1-Distill-Llama-70B FP8 trên một DGX Spark (ngân sách 108.80 GB, workspace 2 GiB): bao nhiêu request 8K?DeepSeek-R1-Distill-Llama-70B in FP8 on one DGX Spark (108.80 GB budget, 2 GiB workspace): how many 8K requests?

Lời giảiAnswer

13. Weight 70.55 GB, còn 36.10 GB; mỗi request 8K cần 2.5000 GiB KV.

13. Weights are 70.55 GB, leaving 36.10 GB; each 8K request needs 2.5000 GiB of KV.

3. Vì sao NVFP4 ra 0.5625 byte/tham số chứ không phải 0.5?Why is NVFP4 0.5625 bytes per parameter rather than 0.5?

Lời giảiAnswer

Mỗi khối 16 giá trị 4 bit có thêm một scale FP8 (8 bit): 4 + 8/16 = 4.5 bit. Checkpoint thật còn lớn hơn vì embedding, norm, router thường giữ BF16.

Every block of 16 four-bit values carries one FP8 (8-bit) scale: 4 + 8/16 = 4.5 bits. Real checkpoints are larger still because embeddings, norms and routers usually stay BF16.

4. Có hai DGX Spark (256 GB). DeepSeek-V3 ở FP8 có vừa không? NVFP4 thì sao?Two DGX Sparks (256 GB). Does DeepSeek-V3 fit in FP8? In NVFP4?

Lời giảiAnswer

Không. FP8 cần 671.03 GB, NVFP4 cần 377.45 GB, cả hai vượt 256 GB trước khi tính KV.

No. FP8 needs 671.03 GB, NVFP4 377.45 GB; both exceed 256 GB before any KV.

5. Bạn tính Qwen3-8B ra 8,190,735,360 tham số. Kiểm thế nào là đúng mà không tải weight?You computed 8,190,735,360 parameters for Qwen3-8B. How do you verify without downloading weights?

Lời giảiAnswer

Đọc metadata.total_size trong model.safetensors.index.json: checkpoint BF16 phải là 2 × 8,190,735,360 = 16,381,470,720 byte.

Read metadata.total_size in model.safetensors.index.json: a BF16 checkpoint must be 2 × 8,190,735,360 = 16,381,470,720 bytes.
