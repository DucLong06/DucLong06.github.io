GQA, MLA, MoEGQA, MLA, MoE

Nhận diện kiến trúc attention và MoE, rồi tính byte KV và lượng đọc expert.Spot the attention and MoE architecture, then compute KV bytes and expert reads.

Quy ước số: mọi con số trong bài in đúng như output của course/m1/calc.py hoặc của lệnh lab.

Number convention: every number is printed exactly as course/m1/calc.py or the lab command outputs it.

1

Mục tiêuGoal

Học xong, bạn nhìn config.json và shape weight của một model là nói được nó dùng MHA, GQA, MQA hay MLA, có MoE hay không, rồi tính được KV byte/token và lượng weight expert phải đọc mỗi bước cho một batch.

After this lesson, from a model's config.json and weight shapes you can tell whether it uses MHA, GQA, MQA or MLA and whether it is MoE, then compute its KV bytes per token and the expert weights read per step for a batch.

2

Vì sao cầnWhy it matters

Đội vận hành cần chọn model cho dịch vụ hỏi đáp tài liệu dài trên DGX Spark. Hai câu hỏi thực tế: (1) “Mỗi request 128K token giữ bao nhiêu KV?” Với shape GQA của Qwen3-8B là 18.00 GiB (và vượt cửa sổ gốc 40,960 token của nó), còn MLA của DeepSeek-V3 chỉ 8.58 GiB dù model lớn hơn nhiều. (2) “Qwen3-30B-A3B chỉ có 3.35 B tham số active, vậy có nhẹ như model 3B không?” Về FLOPs thì gần như vậy, nhưng bộ nhớ phải chứa đủ 30.53 B tham số, và khi batch 64 token rải đều trên mọi expert thì mỗi tầng phải đọc 1,152 MiB weight expert thay vì 72 MiB (tính bởi course/m1/calc.py). Kiến trúc quyết định cả dung lượng lẫn lượng đọc.

The team must pick a model for a long-document Q&A service on DGX Spark. Two practical questions: (1) “How much KV does one 128K-token request hold?” With Qwen3-8B's GQA shape it is 18.00 GiB (and beyond its native 40,960-token window), while DeepSeek-V3's MLA needs only 8.58 GiB although the model is far larger. (2) “Qwen3-30B-A3B has only 3.35 B active parameters, so is it as light as a 3B model?” In FLOPs, nearly; but memory must hold all 30.53 B parameters, and when a batch of 64 tokens spreads over every expert, each layer reads 1,152 MiB of expert weights instead of 72 MiB (computed by course/m1/calc.py). Architecture decides both capacity and read volume.

3.1 MHA, GQA, MQA: bớt số bộ K, V

3.1 MHA, GQA, MQA: fewer K, V sets

MHA cho mỗi query head một cặp K, V riêng; MQA cho mọi query head dùng chung một cặp; GQA chia query head thành nhóm, mỗi nhóm một cặp. Số token không đổi, số bộ K, V mỗi token giảm. Với shape của Qwen3-8B (36 tầng, 32 query head, d_h = 128, BF16):

MHA gives every query head its own K, V pair; MQA shares one pair across all query heads; GQA groups query heads and gives each group one pair. The token count is unchanged; the number of K, V sets per token drops. With the Qwen3-8B shape (36 layers, 32 query heads, d_h = 128, BF16):

Biến thểVariantKV headByte/tokenBytes/tokenContext 8K
MHA32589,824 B (576 KiB)4.500 GiB
GQA (thật, 4 query head mỗi KV head)GQA (real, 4 query heads per KV head)8147,456 B (144 KiB)1.125 GiB
MQA118,432 B (18 KiB)0.141 GiB

GQA giảm KV và projection K, V, nhưng 32 query head vẫn tính điểm riêng, nên FLOPs attention (QKᵀ, A·V) không giảm theo.

GQA cuts KV and the K, V projections, but all 32 query heads still score separately, so attention FLOPs (QKᵀ, A·V) do not drop with it.

3.2 MLA: bớt số chiều mỗi token

3.2 MLA: fewer dimensions per token

MLA (DeepSeek-V2, V3) không gộp head mà nén: hidden vector chiếu xuống một latent c rộng kv_lora_rank = 512, rồi mới chiếu lên K, V từng head khi cần. Nhờ tính kết hợp qKᵀ = q(c·U_k)ᵀ = (q·U_kᵀ)·cᵀ, lúc decode chỉ cần lưu c và biến đổi query trước. RoPE không đi qua được phép “hấp thụ” này, nên DeepSeek tách thêm một key RoPE chung qk_rope_head_dim = 64 chiều. Mỗi token mỗi tầng lưu 512 + 64 = 576 giá trị.

Shape thật của DeepSeek-V3 (lab): kv_a_proj_with_mqa [576, 7168] ra đúng 576 chiều (latent + RoPE key); kv_b_proj [32768, 512] mở latent thành 128 head × (128 nope + 128 value) = 32,768. Tính bởi course/m1/calc.py:

MLA (DeepSeek-V2, V3) compresses instead of grouping: the hidden vector is projected down to a latent c of width kv_lora_rank = 512, and only expanded to per-head K, V when needed. Because qKᵀ = q(c·U_k)ᵀ = (q·U_kᵀ)·cᵀ, decode can store only c and transform the query first. RoPE cannot pass through this absorption, so DeepSeek adds a separate shared RoPE key of qk_rope_head_dim = 64. Each token stores 512 + 64 = 576 values per layer.

DeepSeek-V3's real shapes (lab): kv_a_proj_with_mqa [576, 7168] outputs exactly those 576 dims; kv_b_proj [32768, 512] expands the latent into 128 heads × (128 nope + 128 value) = 32,768. Computed by course/m1/calc.py:

  • Cache gọn (compact) = 61 tầng × 576 × 2 byte = 70,272 B/token (68.62 KiB); 8K: 549.0 MiB; 128K: 8.58 GiB.
  • Nếu mở ra lưu K, V từng head (expanded): 4,997,120 B/token (4,880.00 KiB); 8K: 38.12 GiB. Chênh x71.1.
  • Ví dụ trong sách với Kimi K3 (24 tầng MLA, 512 + 64, BF16, 8K): 216 MiB.
  • The compact cache is 61 layers × 576 × 2 bytes = 70,272 B/token (68.62 KiB), 549.0 MiB at 8K, 8.58 GiB at 128K.
  • Storing expanded per-head K, V would be 4,997,120 B/token (4,880.00 KiB), 38.12 GiB at 8K, a x71.1 gap.
  • The book's Kimi K3 example (24 MLA layers, 512 + 64, BF16, 8K) gives 216 MiB.

Bài báo DeepSeek-V2 báo MLA giảm KV cache 93.3% so với DeepSeek 67B. Cái giá: mỗi bước decode thêm phép biến đổi query, và lưu lượng vẫn tăng theo context.

The DeepSeek-V2 paper reports MLA cuts the KV cache by 93.3% versus DeepSeek 67B. The cost: an extra query transform per decode step, and reads still grow with context.

3.3 MoE: lưu nhiều, kích hoạt ít

3.3 MoE: store many, activate few

MoE thay FFN dense bằng E expert (mỗi expert là một SwiGLU nhỏ) và một router chọn k expert cho mỗi token. Sách tóm tắt: router cho phép “how many parameters the model stores” và “how many parameters a token activates” được chỉnh riêng (Bojie Li, Understanding AI Infra, Ch. 2).

MoE replaces the dense FFN with E experts (each a small SwiGLU) and a router that picks k experts per token. In the book's words, routing lets “how many parameters the model stores” and “how many parameters a token activates” be tuned separately (Bojie Li, Understanding AI Infra, Ch. 2).

ModelModelE / kTổngTotalActiveTỉ lệRatio
Qwen3-30B-A3B128 / 830.53 B3.35 B11.0%
DeepSeek-V3256 / 8 (+1 shared)671.03 B37.55 B5.6%

Qwen3-30B-A3B: một expert 3·d·f_e = 4,718,592 tham số (9 MiB BF16); toàn bộ expert một tầng 1,152 MiB; 8 expert một token chọn: 72 MiB.

Batch đổi lượng đọc. Batch decode 64 token, mỗi token chọn 8 expert: 512 lượt dispatch. FLOPs expert mỗi tầng như nhau trong mọi trường hợp: 4.83 GFLOP. Nhưng lượng weight phải đọc phụ thuộc số expert khác nhau U bị chạm tới: rải đều thì U=128, đọc 1,152 MiB mỗi tầng; dồn vào 8 expert thì U=8, đọc 72 MiB. Chênh x16. (Sách làm ví dụ tương tự với Qwen3.6: 256 expert, chênh 32 lần.)

For Qwen3-30B-A3B, one expert is 3·d·f_e = 4,718,592 parameters (9 MiB BF16), all experts of one layer 1,152 MiB, and the 8 experts one token picks 72 MiB.

Batching changes reads. A decode batch of 64 tokens, 8 experts each: 512 dispatches. Expert FLOPs per layer are the same either way: 4.83 GFLOP. But weight reads depend on how many distinct experts U are touched: spread evenly, U=128 and each layer reads 1,152 MiB; concentrated on 8 experts, U=8 and it reads 72 MiB. A x16 gap. (The book runs the same example on Qwen3.6 with 256 experts: a 32-fold gap.)

Key notesKey notes

  1. GQA/MQA giảm số bộ K, V; MLA giảm số chiều mỗi token; cả hai giảm byte KV, không bỏ được việc đọc KV tăng theo context.
  2. Nhận diện qua config: num_key_value_heads < num_attention_heads là GQA (bằng 1 là MQA); có kv_lora_rank là MLA.
  3. Qwen3-8B: MHA 576 KiB, GQA 144 KiB, MQA 18 KiB mỗi token. DeepSeek-V3 MLA: 68.62 KiB mỗi token cho model 671 B.
  4. GQA không giảm FLOPs attention: query head vẫn tính riêng.
  5. MoE: bộ nhớ theo tổng tham số, FLOPs theo active. Qwen3-30B-A3B active 11.0%, DeepSeek-V3 active 5.6%.
  6. Ở batch lớn, MoE có thể phải đọc gần hết expert mỗi bước (Qwen3-30B-A3B: 1,152 MiB so với 72 MiB mỗi tầng): lợi thế “ít active” về đọc bộ nhớ giảm dần khi batch tăng.
  1. GQA/MQA cut the number of sets of K, V; MLA cuts the dimensions per token; both shrink KV bytes, neither removes context-proportional KV reads.
  2. Spot them in the config: num_key_value_heads < num_attention_heads means GQA (1 means MQA); a kv_lora_rank field means MLA.
  3. Qwen3-8B: MHA 576 KiB, GQA 144 KiB, MQA 18 KiB per token. DeepSeek-V3 MLA: 68.62 KiB per token for a 671 B model.
  4. GQA does not cut attention FLOPs: query heads still compute separately.
  5. MoE: memory follows total parameters, FLOPs follow active. Qwen3-30B-A3B is 11.0% active, DeepSeek-V3 5.6%.
  6. At large batch, MoE may read almost every expert per step (Qwen3-30B-A3B: 1,152 MiB vs 72 MiB per layer): the memory-read advantage of “few active” fades as the batch grows.

Đối chiếu.

  • DeepSeek-V3: bỏ 5 tensor weight_scale_inv (scale FP8 theo khối 128 × 128: 280 + 1,024 + 7,168 + 672 + 2,304), phần weight còn lại khớp DeepSeek-V3 MLA weights per layer (no FP8 scales) 187,107,328 của calc.py. Dòng [576, 7168] là bằng chứng KV mỗi token mỗi tầng chỉ 576 giá trị.
  • Qwen3-30B-A3B: router gate.weight [128, 2048] = 128 expert; mỗi expert 3 × 1,572,864 = 4,718,592 tham số, khớp dòng one expert params của calc.py.

Trên máy có GPU chạy vLLM: so số KV token in lúc khởi động giữa một model GQA và một model MLA cùng --gpu-memory-utilization; model MLA phải chứa nhiều token hơn trên mỗi GB còn trống.

Cross-check.

  • For DeepSeek-V3, drop the 5 weight_scale_inv tensors (FP8 block scales for 128 × 128 tiles: 280 + 1,024 + 7,168 + 672 + 2,304) and the remaining weights match calc.py's DeepSeek-V3 MLA weights per layer (no FP8 scales) 187,107,328. The [576, 7168] line is the evidence that KV per token per layer is only 576 values.
  • For Qwen3-30B-A3B, the router gate.weight [128, 2048] means 128 experts; each expert is 3 × 1,572,864 = 4,718,592 parameters, matching calc.py's one expert params line.

On a GPU machine with vLLM: compare the KV token count printed at startup for one GQA and one MLA model under the same --gpu-memory-utilization; the MLA model should fit more tokens per free GB.

Tự kiểm traSelf-check

1. Config có num_attention_heads: 64, num_key_value_heads: 8, head_dim: 128, 80 tầng. Đây là gì, và KV BF16 mỗi token bao nhiêu?A config has num_attention_heads: 64, num_key_value_heads: 8, head_dim: 128, 80 layers. What is it, and how much BF16 KV per token?

Lời giảiAnswer

GQA (64 query head dùng chung 8 KV head). 2 × 80 × 8 × 128 × 2 = 327,680 B (đây là DeepSeek-R1-Distill-Llama-70B ở bài 04).

GQA (64 query heads sharing 8 KV heads). 2 × 80 × 8 × 128 × 2 = 327,680 B (the DeepSeek-R1-Distill-Llama-70B of lesson 04).

2. Đổi Qwen3-8B từ GQA sang MQA thì FLOPs attention mỗi cặp query-key có giảm không?Switching Qwen3-8B from GQA to MQA: do attention FLOPs per query-key pair drop?

Lời giảiAnswer

Không. KV còn 18 KiB/token nhưng 32 query head vẫn tính điểm và gộp V riêng: 16,384 FLOPs mỗi cặp mỗi tầng như cũ.

No. KV falls to 18 KiB/token but all 32 query heads still score and aggregate V separately: 16,384 FLOPs per pair per layer as before.

3. Vì sao DeepSeek-V3 lưu 576 chứ không phải 512 giá trị mỗi token mỗi tầng?Why does DeepSeek-V3 store 576 rather than 512 values per token per layer?

Lời giảiAnswer

512 là latent; thêm 64 chiều key RoPE tách riêng, vì RoPE phụ thuộc vị trí nên không hấp thụ được vào phép biến đổi query.

512 is the latent; 64 more dims hold the decoupled RoPE key, since position-dependent RoPE cannot be absorbed into the query transform.

4. Qwen3-30B-A3B ở batch 64: FLOPs expert như nhau giữa rải đều và dồn, vì sao lượng đọc chênh x16?Qwen3-30B-A3B at batch 64: expert FLOPs are equal for spread and concentrated routing, so why do reads differ x16?

Lời giảiAnswer

FLOPs theo tổng lượt dispatch (512, không đổi); lượng đọc theo số expert khác nhau bị chạm: 128 so với 8, mỗi expert 9 MiB.

FLOPs follow total dispatches (512, unchanged); reads follow distinct experts touched: 128 vs 8, at 9 MiB each.

5. DeepSeek-V3 có 37.55 B active. Có chạy được trên máy chỉ đủ chứa 40 B tham số không?DeepSeek-V3 has 37.55 B active. Can it run on a machine that only holds 40 B parameters?

Lời giảiAnswer

Không. Phải chứa đủ 671.03 B tham số vì mỗi token có thể chọn expert bất kỳ; active chỉ nói về FLOPs và lượng đọc mỗi token.

No. All 671.03 B parameters must be resident because each token may pick any expert; active only describes per-token FLOPs and reads.
